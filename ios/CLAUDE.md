# Namma Metro (iOS)

SwiftUI app (iOS 17+, Swift 5.9) that shows Bengaluru Namma Metro trains on a map and per-station arrivals.
No third-party dependencies. The Xcode project is generated by XcodeGen from `project.yml`; never edit or commit `*.xcodeproj`.

## Commands
- Generate project: `xcodegen generate` (re-run after adding/removing files or editing `project.yml`; it resets signing settings)
- Build/test: `xcodebuild test -project NammaMetro.xcodeproj -scheme NammaMetro -destination 'platform=iOS Simulator,name=iPhone 16' CODE_SIGNING_ALLOWED=NO`
- Run on device: signing (team Y853R8D4N4, `com.ajinkya.nammametro`) lives in `project.yml`. Build with `-configuration Release -destination 'id=<UDID>' -allowProvisioningUpdates`, then `xcrun devicectl device install app`.
- Regenerate track data: `python3 tools/build_track.py` (fetches OpenStreetMap; writes `Resources/metro_track.json`).
- Simulator shortcuts (debug builds): launch args `-autoRide <line> [-rideNear <stationID>] [-rideCamera Follow|Front|Trackside] [-skyHour 19.5]` open the 3D view directly.

## Layout
- `NammaMetro/Models.swift`: `Station`, `MetroLine`, `Train`, `Arrival`, and the `TrainFeed` protocol (the single data-source seam).
- `NammaMetro/StationData.swift`: `MetroNetwork` (Purple, Green, Yellow lines): station names in line order; positions and track come from `Resources/metro_track.json` (OSM, generated by `tools/build_track.py`, stop order must match).
- `NammaMetro/Track.swift`: `TrackGeometry` (alignment every 8 m, deck height for viaduct/ramp/tunnel, station distances) and `MetroWorld` (Mercator-based local metres; x east, z south). `Train.distance` is metres along this track.
- `NammaMetro/Ride/`: SceneKit 3D ride view opened by tapping a train on the map. `TrainModel` (procedural 6-car train, look per `design/reference/`), `TrackScenery` (viaduct/rails/piers/stations, streamed in 400 m chunks), `GroundTiles` (MapKit satellite snapshots), `Sky` (real sun position), `RideScene` (controller: render loop, cameras, x-ray underground), `RideView` (SwiftUI + HUD).
- `NammaMetro/ScheduleFeed.swift`: `TrainFeed` from BMRCL's published timetable (`Timetable.swift`, `Resources/timetable.json`), every trip including peak short loops, in Asia/Kolkata time. Called every frame from the 3D view's render thread: keep it immutable and index-based (no full scans, no mutable state).
- `tools/build_timetable.py`: regenerates `timetable.json` from github.com/Vonter/bmrcl-gtfs (ODbL; keep the attribution shown in the app). Re-run when BMRCL publishes a new timetable; it patches official last trains the feed rounds away.
- `NammaMetro/Planner.swift` (routes, fares by stations travelled), `Calibration.swift` (`CalibratedFeed`: rider sightings shift a line/direction for 90 min), `TripTracker.swift` (active journey, alerts, GPS sync), `PlanScreen.swift`, `TripScreen.swift`.
- `NammaMetro/MapScreen.swift`, `StationsScreen.swift` (also holds `StationDetailView`), `NammaMetroApp.swift`: UI.
- `NammaMetroTests/`: XCTest unit tests (`TimetableTests` checks the feed against BMRCL's published first/last trains).

## Conventions and gotchas
- UI must depend on `TrainFeed`, not `ScheduleFeed`. A real-time source = a new `TrainFeed` implementation plus a one-line change in `NammaMetroApp.swift`.
- BMRCL has no public realtime feed. Anything shown from `ScheduleFeed` is an estimate and the UI says so (`isEstimated`); keep that label.
- Terminal departures are BMRCL's; intermediate station times are modelled (BMRCL doesn't publish them), typically within 2 min. The Pink line isn't in the data yet (opening expected late Oct 2026).
- `Calibration.offset` is read from the render thread: it goes through a lock-protected snapshot; UI reads the observed `offsets`.
- 3D: train nodes are clones sharing geometry/materials; one mesh per car (~11 draw calls). Build heavy geometry with `MeshBuilder`, not SCNNode hierarchies. Shared state between render and main thread goes through `RideSceneController.shared` + lock.
- Keep MapKit `Map` content small: split into helper functions marked `@MapContentBuilder` (one large nested closure caused "Generic parameter 'Content' could not be inferred").
- This code was authored without a Swift toolchain; if a build error appears, fix it from the compiler output rather than assuming earlier code compiled.
